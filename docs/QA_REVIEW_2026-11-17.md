# Rentigo QA review — 17 November 2026

Reviewed the current working tree on `chore/scaffold-stitch-homepage`, including uncommitted and untracked implementation files. This is a regression review of the current development milestone, not approval for deployment or the next phase. No application code was changed.

The foundation, sample browsing and local credential authentication generally work. Two reproducible issues remain. Real rental operations remain intentionally unavailable.

## Issues to fix

### 1. Existing email can produce a false registration success

Location: `src/components/shared/auth-form.tsx:38` (success copy at line 59).

1. Register a development test account and sign out.
2. Register again with the same email, a different available username and a different password.
3. The form clears and displays **Your account is ready**, instructing the person to sign in with the credentials they just chose.
4. Sign-in with the second username/password fails: that registration did not create an account.

With `autoSignIn: false`, the installed Better Auth implementation deliberately returns a generic HTTP 200 and synthetic user for an existing email to prevent account enumeration. `response.ok` therefore does not prove that an account was created. The backend's generic response is expected; the UI's definite success claim is the defect. Preserve the privacy protection and use accurate, noncommittal confirmation/next-step copy unless account creation can be established safely. Priority: P2.

### 2. Long profile email overflows on mobile

Locations: `src/app/(protected)/profile/page.tsx:6` and `.definition-row` in `src/app/globals.css:78`.

1. Sign in with an email such as `rentigo_qa_1794894627399@example.invalid`.
2. Open `/profile` at 320px or 390px viewport width.
3. The email extends beyond the card. At 320px it also causes substantial horizontal page overflow; at 390px a smaller overflow remains. The email text is visibly clipped/outside the card.

The profile uses a flex definition row without allowing the unbroken email value to shrink and wrap. Allow the value to shrink/wrap (for example, `min-width: 0` and `overflow-wrap: anywhere`) or stack profile rows on narrow screens. Priority: P2.

## Limits and observations

- Current configuration uses `rentigo_development`, with the localhost-only email-verification exception. Email delivery, Google credentials and Cloudinary are not configured/enabled.
- Email verification, recovery email delivery, reset-token expiry/reuse, Google OAuth, session expiry over time, restricted-account behavior with an actual restricted user, and successful admin access remain unverified. No admin/restricted user was provisioned for this review.
- Real listings/uploads, availability, bookings, messages, reports, payments and provider integrations are not implemented; their preview rendering and disabled actions were tested, not business workflows.
- Rate-limit durability/concurrency, load/performance, a full accessibility audit, other browser engines and physical mobile devices were not tested. A successful build and these checks cannot guarantee all possible inputs or future integrations.
- Browser logs contained the existing smooth-scroll configuration warning and one transient RSC-fetch fallback during development navigation. The destination ultimately rendered; no reproducible page failure was established from that diagnostic, so it is not listed as a confirmed defect.
- One labelled development account, `rentigo_qa_1794894627399`, was retained. All its QA sessions were revoked at the end. No real user records were edited, no emails were sent, and no production resources or payments were used.
- The temporary production QA server was stopped; the user's existing development server was left running. No deployment or application fixes were performed. Project status was left unchanged because this was a QA pass, not a completed feature milestone.
